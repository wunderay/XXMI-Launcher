# XXMI first-visit readiness

Campaign ID: `xxmi-first-visit-exec-20261028` (fresh executable admission; predecessor `xxmi-first-visit-readiness` remains a draft).

Repository: the authorized writable XXMI launcher repository, with a narrowly bound native source baseline. This document does not register a repository, activate a draft, admit quests or prove executor readiness.

## Outcome

Make a verified, selected set of complete supported mod resource groups ready before their first use, so their first character visit approaches revisit behavior without source I/O, decode, shader compilation, object/view creation or worker waits on that selected group's first-draw path. Preserve original texture quality, mutation independence, ordinary launch/injection behavior and existing revisit performance.

Report unsupported, incomplete, unselected and over-budget groups honestly. Finite capacity does not establish readiness for every on-disk mod, every character or every first visit.

## Authorization and boundaries

The user requested executable Guild work on 2026-10-28. Reuse the existing first-visit design and evidence; do not repeat its planning as the implementation deliverable. Work may create source changes, isolated builds, fixtures and reviewable campaign artifacts under the approved Projects repositories. Preserve unrelated installer/antivirus work and all existing dirty changes.

The user launches the game through the existing approved diagnostic workflow. Do not start the game, request new elevation, weaken signatures or authentication, change Defender/security settings, publish a release, sign a package, change the normal installation or introduce automatic game launches. Previously approved isolated diagnostic deployment must remain within its exact existing scope; do not infer normal-installation permission from it.

Keep preparation limits at 3 GiB CPU and 2 GiB GPU. Longer explicit startup preparation is authorized; an unbounded startup or page-cache warmer is not. Retain the current 120-second cooperative startup limit unless a later concrete change is authorized. No speculative creation during ordinary gameplay, Present-gap loading-window inference, estimate halving, texture resizing, recompression or mip stripping.

## Current evidence and source

The inspected development record already implements actual-device startup GPU preparation, private per-declaration objects, bounded retention, generation fences, raw-size CPU admission and original-quality paths. Prior fixtures report source-read-denied first-use reuse, mutation isolation, descriptor rejection and zero speculative creation across 100 later Presents. These are historical synthetic results, not a new test result and not a measured game speedup.

The saved first-use counters show CPU misses 235, GPU misses 123, hits 29, invalidated 19, unavailable 0 and unsupported 3. They are cumulative, orderless lookup outcomes; they do not establish unique character counts, latency or the cause of the misses. Preserve the original observations rather than attributing them to declaration order, pressure or deadline without new evidence.

See `SOURCE-BASELINE.md` for the smallest candidate portable input set. The existing launcher checkout is dirty on a branch containing unrelated installer changes, while the latest native source is beneath ignored `.guild-data/loading-followup/native`. An ignored absolute path is not a worker contract. Before remote work, bind the current source into an authorized portable input commit/artifact and demonstrate byte-for-byte reconstruction. Do not use the launcher's current branch name or the legacy native parent alone as the candidate identity.

## Required behavior

1. Account for preparation by source/config/device generation and stable resource/group identities. Record bounded admission, retry, CPU/GPU rejection, requested/retained bytes, creation cost, pass end, pressure, eviction and invalidation outcomes. Relate first-use costs to monotonic timestamps and Present intervals. No synchronous per-draw filesystem writes, unbounded identifiers or new mandatory tracing toggle for basic coverage.
2. Resolve supported dependency closures from parsed command/resource semantics. Directory proximity, INI proximity and a draw observation are hints, not proof that a closure is complete. Dynamic/unresolved routes retain explicit incomplete reasons and compatible fallback.
3. Preserve bounded useful observations even when speculative learning is disabled, with independent controls and content/config identity. Rank complete groups by measured avoidable cost, frequency and footprint; reject stale profiles. Retain original conservative estimates until a measured, independently reviewed replacement is justified.
4. During the explicit startup pass, prepare complete selected closures on the actual game device, including required views. First use reuses the exact qualified private object/view; per-declaration mutations remain independent. Releasing CPU staging bytes must not convert a valid GPU hit into a CPU miss or weaken freshness verification.
5. Under pressure, evict ranked preparation-owned groups toward an explicit byte target. Preserve game-owned resources, safe generation invalidation and revisit behavior. Never silently clear all retained groups as a substitute for accountable policy. Bounded retries must terminate or explain why a selected closure remains incomplete.
6. Show selected/admitted/complete/incomplete coverage and reasons separately from total on-disk inventory. Connect this to the existing development launcher/capture flow with no new compulsory gameplay wait or extra launcher click.

## Validation and completion

Bind every build and report to exact launcher source, reconstructed native source digest/commit, patch chain, generated version header, compiler/SDK, build command and resulting production/fixture DLL hashes. Rebuild all affected translation units; a final candidate requires clean full production and fixture builds. Test-only exports must be absent from production.

Use focused CPU/native/actual-device WARP fixtures for dependency closure and unsupported paths; deterministic group ranking; budget accounting and bounded retries; source/config/device invalidation; immutable verification after CPU staging release; mutation isolation; view reuse; pressure eviction; cancellation; and absence of speculative creation after startup. Extend collector tests only for changed contracts. Observe resource limits and use one local Guild adventurer; native compile concurrency must fit the assigned quest's current resource budget rather than assuming four workers.

Actual-game success requires user-run matched sessions with the same hardware/driver, active mod contents, effective settings, character/visit sequence and exact loaded DLL identity. Measure first visit versus revisit, startup overhead, first-correct-frame latency, frame-time distributions, F10, pressure and visual correctness. Establish tolerances from baseline variability before candidate acceptance. Native Present timestamps alone do not prove displayed-frame latency; keys alone do not prove appearance. Preserve raw captures and loss/accounting failures.

Separate statuses: implementation/fixture qualification, selected-scenario actual-game qualification, and full release qualification. A missing user-run capture blocks performance acceptance, not independent source work. Existing `qualify.py` release gates stay intact; do not lower their thresholds to pass this campaign. Full publisher release/signing remains a separate external gate. Campaign completion must never imply it.

Accept the selected-scenario goal only after independent review binds the exact candidate/evidence, confirms complete/correct first appearance, no selected first-use I/O/creation/wait, and no material startup/F10/revisit/frame-pacing regression under the agreed protocol. Otherwise record the exact unresolved result as NOT PROVEN and retain a runnable, safely reversible candidate.
